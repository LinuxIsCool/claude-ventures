Three Architectural Approaches

The pivotal question: how do Projects and Milestones live on disk?

A

Fully Flat — three sibling directories

Each entity type gets its own flat directory at the same level. Parent-child relationships encoded only in parent_id frontmatter. No stage subdirs for projects/milestones — stage is just a YAML field.

~/.claude/local/
ventures/active/indigenomics-ai.md
ventures/dormant/salish-sea-dreaming.md
projects/data-platform.md ← venture_id: indigenomics-ai
projects/governance-model.md ← venture_id: indigenomics-ai
projects/herring-pipeline.md ← venture_id: salish-sea-dreaming
milestones/schema-design.md ← project_id: data-platform
milestones/api-layer.md ← project_id: data-platform

Pros

  • Stage transitions = frontmatter only, no file moves
  • Simplest store code
  • Research agent recommendation

Cons

  • All projects mixed together in one dir
  • Not human-readable at filesystem level
  • Harder to understand without tooling
B

Parent-Grouped — nested by parent, flat by stage

Projects live inside a sibling directory to their venture file. Milestones live inside a sibling to their project file. No stage subdirectories for child levels — stage is just a YAML field. When a venture changes stage, only the venture file moves; child directories stay in place (resolved by parent_id).

~/.claude/local/ventures/active/
indigenomics-ai.md
indigenomics-ai/ ← sibling dir
data-platform.md stage: active (in YAML)
governance-model.md stage: planned
data-platform/ ← project's child dir
schema-design.md
api-layer.md
Venture moves stage → only .md moves. Children stay put via parent_id.

Pros

  • Human-readable filesystem structure
  • Children co-located with parent
  • Intuitive when browsing manually

Cons

  • Children appear abandoned when venture changes stage (dir stays behind)
  • Slightly more complex store
C

Hybrid — projects first-class, milestones embedded

Promote only Projects to first-class files (separate directory). Keep Milestones embedded in project YAML. This is a half-step upgrade — meaningful Projects get full lifecycle, Milestones stay lightweight and fast to create.

~/.claude/local/ventures/active/indigenomics-ai.md
~/.claude/local/projects/data-platform.md
milestones: ← still embedded YAML
- id: ms-schema
title: Schema Design
status: complete
completion_criteria: [...]

Pros

  • Simpler than full fractal
  • Milestones are lightweight — quick to add
  • Minimal migration effort

Cons

  • Not truly fractal — milestones don't get own lifecycle
  • Project files grow large with many milestones
  • Can't query milestones independently

My recommendation: B (parent-grouped)

Option A is technically cleaner but loses the filesystem legibility that makes markdown-based tools valuable — the whole point is that you can browse and edit files directly. Option B gives you human-readable structure AND avoids the stage-subdir problem by keeping child entities' stages in YAML only. The "orphaned directory" when a venture changes stage is solved by the parent_id: when querying, the store ignores directory location and resolves children by ID.
