How Does a Venture "Know" Its Children?

Three approaches — pick one

A

Filesystem as truth — computed view

The venture .md file contains only venture-level data. Projects live in a sibling directory indigenomics-ai/projects/. The MCP server assembles the full picture by scanning the directory tree at query time — no project data is stored in the venture file itself.

indigenomics-ai.md
  stage: active
  priority: high
  co_venturers: [...]
  financial: {...}
  # no projects: key
indigenomics-ai/projects/active/
  data-platform.md ← discovered by scan
  governance.md ← discovered by scan

Pros

  • Zero redundancy
  • Children can be created independently
  • File stays small forever

Cons

  • Venture view requires directory scan
  • Slightly slower reads
B

Cached rollup in frontmatter

The venture .md file contains venture-level data plus a cached summary of its projects (title, stage, completion%). Projects still live in their own files — but the venture caches a lightweight digest that's updated whenever a child changes.

indigenomics-ai.md
  stage: active
  projects_summary:
    - id: prj-abc
      title: Data Platform
      stage: active
      completion: 40%
    # refreshed on write

Pros

  • Fast venture reads
  • Human-readable summary in file

Cons

  • Redundant data → stale cache risk
  • Writes touch venture file on every project update
C

Hybrid — file is index, view is computed

The venture .md file stores venture-level metadata plus a flat list of project IDs. Full project data lives in child files and is resolved at query time. The venture file is a stable index, not a cache — IDs don't go stale.

indigenomics-ai.md
  stage: active
  priority: high
  projects:
    - prj-abc123  # just IDs
    - prj-def456
  # full data lives in child files

Pros

  • No stale cache
  • Explicit ownership relationship
  • Easy to reattach orphaned projects

Cons

  • Must maintain ID list on create/delete
  • Minor sync overhead

My recommendation: Option A

The filesystem already encodes the parent-child relationship via the directory structure. Scanning a directory is cheap (these are small text files). You get zero redundancy and zero sync bugs. The MCP server already scans stage directories to find ventures — extending this to scan projects/ subdirectories is the same pattern. The venture file stays clean.
